📖一、项目概述

Sapphire Studio 是一个 AI 工作站，提供流式 AI 对话、Tool Calling（天气/时间/计算/联网搜索）、Markdown 富文本渲染。内置双 Agent 系统：快速应答 + 深度推理。

import { createOpenAI } from "@ai-sdk/openai";

// 懒加载：模块导入时不立即初始化（key 缺失不会炸）
let _deepseek = null;
function getClient() {
  if (!_deepseek) {
    const key = process.env.DEEPSEEK_API_KEY;
    if (!key) throw new Error("DEEPSEEK_API_KEY 未配置");
    _deepseek = createOpenAI({ apiKey: key, baseURL: "https://api.deepseek.com/v1" });
  }
  return _deepseek;
}
// Proxy 代理：属性访问时懒加载
export const deepseek = new Proxy({}, { get(_, p) { return getClient()[p]; } });
export const CHAT_MODEL = "deepseek-v4-flash";

🧰六、AI 工具集

文件：src/tools/（每个工具一个目录，barrel 导出在 src/tools/index.ts）。五个工具均在服务端执行，返回值统一包成 ToolResult<T>——含 metadata（来源 / 可信度 / 耗时）和分级 error（错误码 / 是否可重试 / 降级结果）。

工具链长度不由代码限制，由模型自己决定何时停止调用；MAX_STEPS = 12 只是失控安全网，触发时用一次无工具的 streamText 强制收尾。

工具数据源Key说明
webSearchBing / DuckDuckGo免费 主源按环境选（开发 Bing / 生产 DuckDuckGo），另一个自动降级。
cheerio 解析 HTML，8s 超时。返回 degraded 标记 + 按结果条数给可信度。
fetchWebPage任意 URL免费抓取网页正文（cheerio 去脚本/导航），配合 webSearch 做深读。
getWeatherwttr.in免费全球城市天气，JSON API。8s 超时。
getCurrentTimeIntl.DateTimeFormat内置支持时区参数，默认 Asia/Shanghai。
calculate沙箱 new Function()内置Math 函数白名单，无全局访问。

双搜索源 + 环境决定主源

两个源互为备份，主源按环境选（pickPrimarySource()）：

环境主源原因
开发Bing本地网络到 DuckDuckGo 经常超时（实测 8s+ 才降级）
生产DuckDuckGo部署机 IP 更容易被 Bing 拦

主源失败自动降级到另一个；两个都挂了返回 ALL_SOURCES_FAILED（retryable）。

注意：这条规则取代了早期的「中文→Bing、英文→DuckDuckGo」语言路由。查询语言不再影响源的选择。

可信度（confidence）是怎么来的

不是算出来的，是手写的常数——表达的是「这个来源按构造值多少信任」，不是「结果和问题有多相关」：

工具取值
calculate / getCurrentTime0.99（固定）
getWeather0.92（固定）
fetchWebPage0.85（固定）
webSearch唯一有逻辑的：
主源成功 → 结果 ≥3 条 0.85 / 否则 0.7
降级成功 → 结果 ≥3 条 0.75 / 否则 0.6
这带来两个已知问题：① 搜到 10 条结果但答非所问，照样 0.85；② 反思阈值 0.8 和这些取值是两个文件里的独立常数，谁改了数字另一处不会跟着变——曾经就因为「降级恰好等于 0.75 阈值」而永远静默。加测试钉住两者的关系是个便宜防线。
全部免费，零 API Key。只要配好 DEEPSEEK_API_KEY，AI 系统即用。

🌊八、流式数据流

POST /api/chat │ ├─ 1. saveUserMessage(conversationId, userMessage) — fire-and-forget │ └─ ReadableStream.start() │ ├─ 2. 手写 Agent 循环（for step = 1..MAX_STEPS） │ │ │ ├─ streamText({ ..., stopWhen: isStepCount(1) }) ← 只跑一步，循环归我们 │ │ └─ chunk 转发 → SSE { text | tool-call | tool-result | tool-error } │ │ │ ├─ calls = await result.toolCalls │ ├─ calls.length === 0 → break ← 正常出口：模型自己说完了 │ │ │ ├─ workingMessages.push(...responseMessages) ← observation 回填 │ ├─ appendReflectionIfNeeded(...) ← Reflect：自检结果质量 │ │ └─ 有问题 → 追加 user 消息 + SSE { reflection } │ │ │ └─ step === MAX_STEPS → streamFinalAnswer() ← 安全网兜底（无工具收尾） │ ├─ SSE { type: "done", finishReason } ← 整圈只发一次 ├─ saveAssistantMessage() → Supabase（tool_calls JSONB 含 trace 字段） ├─ controller.close() ├─ generateAndSaveTitle() → generateText() → Supabase └─ updateConversationTimestamp() + summarization check (≥20 条触发) Client (chat-store.ts): ├─ SSE 事件消费 → 更新 currentMessages state ├─ reflection 事件 → 盖章到该轮工具记录上 ├─ isSending=false → 移动对话到列表顶部 └─ 5s 后 loadConversations() 取回服务器生成的标题
为什么循环要手写？AI SDK v7 的 streamText 默认 stopWhen: isStepCount(1)。不传 stopWhen 不等于「5 步」也不等于「无限」，而是一轮——工具结果永远进不到第二轮生成。这个默认值曾经让整个 Agent 退化成「单轮工具调用 + 手写补丁」，且没有任何报错。

③ 乐观更新 —— 全流程最关键的一段

// chat-store.ts:174-190
const userMessage: Message = {
  id: crypto.randomUUID(),     // ★ id 由浏览器生成，服务器此刻不知道这条消息存在
  role: "user", content, timestamp: new Date(),
};
const messagesBeforeSend = get().currentMessages;   // ★ 必须在下一行 set 之前快照
set((state) => ({
  currentMessages: [...state.currentMessages, userMessage],   // 立刻上屏
  isSending: true, error: null,
}));
const assistantId = crypto.randomUUID();   // AI 消息的 id 也先占好
  • 为什么叫"乐观"：消息还没存进数据库就先显示了。用户感觉不到延迟，代价是本地和服务器可能不一致。
  • ★ 快照顺序不能反：messagesBeforeSend 必须在 set() 之前取。反了的话，发出去的"历史"里会包含这条新消息，模型会看到重复的用户提问。
  • ★ id 是自己造的：所以前端能在服务器返回之前就更新这条消息，不必等。

⑦ SSE 解析 —— 流式的全部秘密

// chat-store.ts:210-226
const reader = response.body!.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const lines = buffer.split("\n\n");   // SSE 帧以空行分隔
  buffer = lines.pop() || "";           // ★ 残片留到下一轮
  for (const line of lines) { /* JSON.parse(line.slice(6)) */ }
}
★ 这行是最容易写错的地方。网络包会在任意字节位置断开，一个 SSE 帧可能分两次到达。pop() 把最后一个（可能不完整的）片段留在 buffer 里等下一个包拼上。删掉它，就会随机丢事件、或者 JSON.parse 直接抛错。所谓"流式"没有魔法——就是一个 while 循环不停读字节。

两条独立路径，写同一个 state

场景走哪条路写入方
发消息POST /api/chat（SSE）→ 事件驱动客户端逐事件拼出内容
刷新 / 切对话loadMessages() → GET /api/chat/conversations/[id]/messages从 Supabase 读回来

两条路都写 currentMessages，但代码完全不同。出问题时先判断是哪条路断的——这是排查聊天问题最重要的分流。loadMessages 里有一行 timestamp ? new Date(m.timestamp) : new Date()：JSON 传输后 Date 变成字符串，不转的话时间显示会挂。

SSE 事件类型

事件载荷
text{ content: string } — 流式文字增量
tool-call{ toolCallId, toolName, args, step?, thought? } — AI 发起工具调用（step 用于界面按轮分组）

Agent Trace

trace 字段直接挂在 ToolCallRecord 上，随 messages.tool_calls（JSONB）一起落库——零迁移、零新增列，刷新后仍可回放：

interface ToolCallRecord {
  // ...原有字段
  step?: number;        // 第几轮（同轮并行调用共享）
  confidence?: number;  // 工具自报可信度
  latencyMs?: number;   // 工具自报耗时
  thought?: string;     // 调这个工具之前模型说了什么
  reflection?: string;  // 这一轮结果自检的结论
}

前端 chat-message.tsx 按 step 分组渲染成「第 N 轮」区块（只有一轮时不显示标题），并展示模型的思考、工具可信度、以及反思告示。

✏️十、标题生成 & 摘要

标题自动生成

首次对话流结束后，调用 generateText()（共享 deepseek 客户端）根据用户问题生成 5-20 字标题，存入 Supabase。客户端 5 秒后 loadConversations() 拿到。兜底：API 失败时用用户问题前 20 字。

手动编辑标题

hover 对话项时标题右边出现 ✏️ 图标，点击 inline 编辑，Enter 保存 / Escape 取消，PATCH /api/chat/conversations/[id] 持久化。

反思（Reflect）

文件：src/services/agentReflection.ts。每一轮工具结果回填之后，检查它们的质量：

  • success === false → 报出错误码，并按 error.retryable 区分「换参数重试可能有帮助」还是「同样的参数重试不会有帮助」
  • metadata.confidence < 0.8 → 报出「可信度低，可能不相关或信息不足」

有问题就作为一条 user 消息追加进上下文，模型据此决定换关键词重试还是诚实收尾。

刻意不做成额外的 LLM 调用。每轮都让模型自检会让 token 成本翻倍，而工具早就把判断依据放进了 metadata——确定性的活不该交给模型。
已删除：早期的 generateForcedReply()。它是在「循环转不起来」时用第二次不带工具的调用硬补答案的补丁，副作用是把状态文字重复输出一遍。循环修好后整个删掉了；现在只在步数安全网触发时才有 streamFinalAnswer()。

长对话摘要

触发条件：对话消息数达到 20 条时自动触发。使用 summaryService.ts（原始 OpenAI SDK 指向 DeepSeek）摘要前半段历史，存入 conversation_summaries 表。fire-and-forget 执行，不阻塞流式响应。

NEXT_PUBLIC_SUPABASE_ANON_KEY是Supabase 匿名密钥
SUPABASE_SERVICE_ROLE_KEY是绕过 RLS，仅服务端

📐十二、开发模式

添加新 Tool

  1. 建目录 src/tools/myTool/myTool.tool.ts，用 tool({...}) 定义
  2. 返回值统一包成 ToolResult<T>（src/tools/types.ts）——务必带上 metadata.confidence，否则反思步骤无从判断结果好坏
  3. 加入 src/tools/index.ts 的 tools 导出对象
  4. 更新 system prompt（src/config/agents.ts）说明这个能力
  5. 写单测，需要 cheerio 等 Node 库时加 @jest-environment node

添加新 Agent

  1. 在 src/config/agents.ts 的 agents 数组中添加配置
  2. Agent 自动出现在侧栏 — 无需 UI 改动

添加新 API 路由

  1. 在 src/app/api/ 创建路由
  2. 用 requireAuth() 保护
  3. Zod 校验 + 统一 JSON 响应

数据库规范

  • 始终通过 service 层操作，不直接调 Supabase
  • supabase-admin 仅在需要绕过 RLS 时使用
  • DB 字段 snake_case，TS 接口 camelCase

🧪十三、测试

关键要求：每个新功能或修复必须有通过测试后才能标记完成。

测试套件

套件命令覆盖范围
后端单元/集成测试 npm run test:jest API 路由、服务层、工具函数（src/__tests__/）
前端冒烟测试 npm run test:playwright:smoke 核心页面加载、基本导航（@smoke 标签）
E2E 测试 npm run test:playwright:e2e 完整业务流程、用户操作链路
全部测试 npm run test:all 提交前运行以上全部

测试工作流

  1. 为新代码编写/更新测试
  2. 运行 npm run test:jest — 必须通过
  3. 运行 npm run test:playwright:smoke — 必须通过
  4. 运行 npm run test:playwright:e2e — 必须通过
  5. 修复所有失败后重新运行，直到全部通过
提交前必须运行 npm run test:all，全部通过才能提交。
